# Технические решения

Координатор поиска — Степан (Claude). Изменения контракта ниже согласуйте в чате до реализации.

## D1. Архитектура: всё в памяти, без OpenSearch

Корпус ~16 тыс. писем, и поиск всегда идёт внутри одного ящика (~1,3 тыс. писем). Векторы и BM25 держим в памяти процесса: numpy-матрица и свой BM25. Перебор по ящику занимает миллисекунды, а отдельный сервис поиска добавил бы сетевые задержки, настройку и точку отказа. HNSW при таком размере не нужен и только снижает точность.

Стек: Python 3.11+, FastAPI, numpy, sentence-transformers (`deepvk/USER2-base` из `vk_mail_search/embeddings.py`), pymorphy3 для лемм.

## D2. Данные

Архив организаторов в Git не кладём. Путь к распакованному архиву — переменная `VK_DATA_DIR` (каталог с `documents.jsonl`, `queries_dev.jsonl`, `qrels_dev.jsonl`). Индексы и векторы — в `VK_CACHE_DIR` (по умолчанию `.cache/`), тоже вне Git.

Поля: документ — `doc_id`, `synthetic_user` (ящик), `doc_dt` (`ГГГГ-ММ-ДД` или `null`), `doc` (текст письма); запрос — `query_id`, `synthetic_user`, `query`, `query_date`; оценка — `query_id`, `doc_id`, `relevance`.

## D3. Контракт поисковика

Пакет `vk_mail_search/`. Любой поисковик (BM25, векторный, гибрид) реализует:

```python
class Searcher(Protocol):
    def search(self, query: str, mailbox: str, as_of: str | None, k: int) -> list[tuple[str, float]]:
        """Ранжированные (doc_id, score), лучший первым, без повторов, не больше k."""
```

Фильтры обязательны в каждом поисковике: только письма ящика `mailbox`; письма с `doc_dt > as_of` исключаются, с `doc_dt = null` остаются.

Модули: `data.py` (загрузка и модель письма), `evaluate.py` (оценка), `bm25.py`, `dense.py`, `hybrid.py`, `api.py` (FastAPI). Фабрика `build_searcher(name, docs)` в `vk_mail_search/__init__.py` или `searchers.py`.

## D4. Оценка

Одна команда для всех вариантов:

```sh
python -m vk_mail_search.evaluate --searcher bm25 --k 10 --out predictions.jsonl
```

Печатает Recall@K, nDCG@K, MRR@K (формулы как в `search-lab/engine.mjs`, графы `2^rel - 1`) для K = 5, 10, 20 и задержку одного вызова `search` p50/p95/p99 после прогрева. `--pred file.jsonl` оценивает готовую выдачу. Формат выдачи: `{"query_id": "...", "doc_ids": [...]}` по строке на запрос.

Сравниваем варианты только этой командой, на одном наборе и одном K. Результаты записываем в таблицу ниже.

## D5. HTTP API

- `GET /api/search?q=&mailbox=&as_of=&k=10` → `{"took_ms": ..., "results": [{"doc_id", "score", "doc_dt", "subject", "snippet"}]}`. `took_ms` — серверное время от приёма до выдачи.
- `GET /api/mailboxes` → список ящиков с числом писем.
- `GET /api/mailboxes/{mailbox}/docs?offset=&limit=` → письма ящика, новые сверху.
- `GET /api/docs/{doc_id}` → письмо целиком.

Модели и индексы загружаются один раз при старте (`lifespan`), запросы их только читают.

## D6. Гибрид BM25 + векторы

`vk_mail_search/hybrid.py`. Каждый поисковик отдаёт свой топ-`depth` (по умолчанию 100) внутри ящика с фильтром даты, списки сливаются:

- `rrf` (по умолчанию): `сумма w / (rrf_k + место)`. Не зависит от шкалы оценок BM25 и косинуса.
- `score`: оценки каждого списка нормируются в [0, 1] внутри запроса, `сумма w * норма`.

Параметры передаются в имени поисковика:

```sh
python -m vk_mail_search.evaluate --searcher hybrid --k 10
python -m vk_mail_search.evaluate --searcher "hybrid:mode=score,w_bm25=0.4,w_dense=0.6,depth=100" --k 10
python -m vk_mail_search.tune_hybrid --k 10 --json hybrid-grid.json
```

`tune_hybrid` один раз собирает топ-200 обоих поисковиков на всех запросах и быстро перебирает сетку режимов, весов, `rrf_k` и глубины. Выбираем не одиночный максимум, а устойчивую область сетки: настройка идёт на тех же 99 публичных запросах, на которых меряем.

## D7. Дата в запросе — главный сигнал

Все 99 публичных запросов — «<тип писем>, полученные <дата | вчера>», и все 565 релевантных писем пришли ровно в названный день. `vk_mail_search/query_parser.py` выделяет период (точные даты, вчера/позавчера/сегодня, N дней назад, на этой/прошлой неделе, в месяце, в году, «с … по …», 15.10, ISO) и тему без «Найди… полученные…». `vk_mail_search/dated.py` ставит письма периода первыми и ранжирует их внутренним поисковиком по теме; письма вне периода не выбрасываются, а идут после — ошибка разбора только меняет порядок. Без даты в запросе работает внутренний поисковик как есть.

```sh
python -m vk_mail_search.evaluate --searcher dated:bm25 --k 10
python -m vk_mail_search.evaluate --searcher "dated:hybrid:mode=score,w_dense=0.6" --k 10
```

## v1.0 — точка отсчёта (21.11.2026)

Рабочий поисковик `dated:bm25`: период из запроса + BM25 с леммами, префиксами лемм, весом темы, весом служебных слов 0,1 и бонусом темы 0,5. Нейросетей и внешних API нет (0 параметров).

| Набор | Recall@10 | nDCG@10 | MRR@10 |
| --- | ---: | ---: | ---: |
| 99 публичных запросов | 0,9263 | 0,9756 | 0,9832 |
| Перефразировки, часть `tune` (44) | 0,6735 | 0,5968 | 0,6300 |
| Перефразировки, часть `test` (32) | 0,7731 | 0,7029 | 0,7332 |

Скорость: вызов поиска p99 ≈ 12 мс (4 ядра Linux, без HTTP); HTTP на сервере 1 vCPU, loopback, 8 клиентов, 1000 вызовов: p99 98,6 мс при K=10, 119,8 мс при K=100 (замер Тимофея на `cc427e4`, повторяется на v1.0 при обновлении стенда). Индексация ~5 с.

Правило дальше: в dev принимается только то, что на 99 запросах не ниже nDCG@10 0,9706 (v1.0 − 0,005) и сохраняет p99 < 1 с; улучшения моделей доказываются на перефразировках, настройка — только по `tune`.
