## Точность

Публичный набор содержит 16 376 писем в 12 ящиках и 99 запросов. Дополнительная проверка использует **32 перефразировки четырёх отложенных семейств** с той же разметкой, что у соответствующих исходных запросов. Часть исходных публичных запросов использовалась при обучении или выборе параметров, поэтому публичные результаты служат проверкой качества на видимом наборе. Перефразировки проверяют устойчивость к изменению формулировки.

| Поиск | Публичные · Precision@5 | Публичные · Recall@5 | Публичные · Recall@10 | Публичные · nDCG@10 | Перефразировки · Precision@5 | Перефразировки · Recall@5 | Перефразировки · nDCG@10 |
| --- | ---: | ---: | ---: | ---: | ---: | ---: | ---: |
| `dated:bm25` (v1.0) | 0,5333 | 0,8479 | 0,9263 | 0,9756 | 0,4125 | 0,5173 | 0,7029 |
| `period` | **0,5354** | **0,8516** | **0,9322** | **0,9906** | 0,4375 | 0,5437 | 0,7103 |
| `period:cover` | 0,5333 | 0,8496 | 0,9292 | 0,9884 | **0,4438** | **0,5750** | 0,7134 |
| `period` + RuBERT, объединение выдач | **0,5354** | **0,8516** | 0,9306 | 0,9867 | 0,4375 | 0,5687 | **0,7163** |
| Адаптированный RuBERT | 0,4808 | 0,8053 | 0,8725 | 0,9203 | 0,3875 | 0,5401 | 0,6802 |

- У `period` на публичном наборе **265 релевантных писем в первых пяти позициях при возможных 270**. Precision@5 делит число попаданий на все 495 позиций, поэтому даже идеальная выдача здесь ограничена **0,5455**: для многих запросов эталон содержит меньше пяти писем. Для Recall@5 потолок **0,8630**: некоторые запросы имеют больше пяти релевантных писем. У nDCG@10 идеальный результат **1,0000**.
- У всех вариантов в таблице Recall@100 равен **1,0000** на обоих наборах. Прирост на этих датированных запросах надо искать в порядке первых результатов. `period` уточняет порядок в названном периоде по покрытию слов в теме и начале письма, близости слов и символьному сходству. `period:cover` использует другой профиль весов.
- `period:cover` поднимает Recall@5 на отложенных семействах на **3,13 п.п.** относительно `period`. Объединение с RuBERT даёт лучший nDCG@10 на этом срезе. Оно проверено на готовых выдачах, сквозной CPU p99 для объединённого поиска ещё не измерен.

## Задержка на CPU

Windows, Intel Core i5-13420H, один процесс Uvicorn, восемь одновременных клиентов. Для каждого указанного замера прогнали 1 000 успешных HTTP-запросов на 99 публичных формулировках после прогрева. В каждой ячейке сначала указан p99 внутри API по `took_ms`, затем p99 по локальному HTTP с учётом ожидания и готового JSON. Это замер на машине разработки. На оборудовании организаторов задержку измерят заново.

| Движок и прогон | K=5, мс | K=10, мс | K=100, мс |
| --- | ---: | ---: | ---: |
| `period`, повтор для отчёта | 39,5 / 71,2 | **48,7 / 66,4** | — |
| `period:cover`, повтор для отчёта | 81,0 / 106,0 | **63,0 / 98,2** | — |
| `period`, предыдущие замеры | 175 / 349 | 142 / 277 | 295 / 452 |
| RuBERT с адаптером | 133,5 / 137,0 | — | 192,7 / 201,6 |
| RuBERT с тематической моделью | 132,6 / 135,7 | — | 185,1 / 194,8 |

В более раннем прогоне `period` p99 локального HTTP для K=10 достигал 445 мс. Запас до секунды сохранялся в каждом из этих прогонов. У обоих профилей `period` поиск и ранжирование выполняются на CPU без нейросети. [История замеров `period`](https://github.com/ttm545/b2baihacatondamirhuesos/blob/22667972b64f60de9903f03ceb53abefa0486583/docs/period-ranking.md#задержка)

По [условию и разбору](brief.md) ориентир p99 составляет **строго меньше 1 секунды** от получения запроса сервером до готовой выдачи. При сравнении качества здесь проверены K=5, 10 и 100. Точный зачётный K в имеющихся материалах отдельно не подтверждён.

## Что дали эксперименты

- **Дата.** На публичном VK все 99 запросов указывают один день, а все 565 положительных пар query–doc приходятся на него. У v1.0 nDCG@10 составил **0,9756** на исходных запросах, **0,6737** по одной дате, **0,1739** по одной теме и **0,0776** при сдвиге даты на день назад. После удаления даты Recall@100 упал с 1,000 до **0,797** на исходных и до **0,521** на перефразировках. Тест фиксировал исходные целевые письма, поэтому измеряет потерю подсказки. Организатор подтвердил такое же распределение запросов на приватном наборе. Значения метрик приватного набора неизвестны. [Аудит даты, сообщения 075–076](https://github.com/ttm545/b2baihacatondamirhuesos/blob/0a47128373a064a5e76bd357f7ab3df81eb7400a/TEAM_CHAT.md)
- **Компактный RuBERT.** Локальная PyTorch-модель имеет 29,1 млн параметров. Готовая проекция кодирует все 16 376 писем за **6,8–8,7 с после загрузки модели**, индекс занимает **10,22 МБ** на диске. Прямое контекстное кодирование всех писем на том же CPU заняло **91,6 мин**. Поисковый запрос требует одного прохода энкодера. [Методика и запуск](../solutions/tiny_encoder/README.md)
- **Пять независимых обучений.** Отдельные адаптеры для VK, SARA, ART·E, Vectrix и W3C улучшили nDCG@5 на собственных отложенных срезах. Ни один из них не превзошёл прежний VK-адаптер по Recall@5 на отложенных семействах VK. Тематическая модель VK при разбиении по паре «ящик и день» дала на 32 перефразировках **0,5900 Recall@5** и **0,7400 nDCG@10**. В этой проверке модель могла учиться на тех же типах писем из других дней. На 99 исходных запросах в такой проверке получено **0,8260 Recall@5** и **0,9545 nDCG@10**. [Протоколы и результаты обучения](../solutions/tiny_encoder/TRAINING.md)
- **Другие реранкеры.** Эксперименты с MiniLM и другими cross-encoder-моделями проверили ограничение времени и возврат базовой сортировки. Отдельная ветка Jina реализует локальный реранк первой десятки. Подтверждённых значений качества и CPU p99 для Jina в её ветке пока нет. [Замеры пилота](https://github.com/ttm545/b2baihacatondamirhuesos/blob/090ebd0/docs/rerank.md) · [Ветка Jina](https://github.com/ttm545/b2baihacatondamirhuesos/tree/7bc286c1c21c1cc185fe78162f274c269bac743b/solutions/jina_rerank)

## Воспроизведение и демо

1. Возьмите [`2266797`](https://github.com/ttm545/b2baihacatondamirhuesos/tree/22667972b64f60de9903f03ceb53abefa0486583) в отдельном checkout, установите `requirements-baseline.txt` и `requirements-api.txt`, распакуйте [архив VK](https://cloud.mail.ru/public/8S62/oQDJV17v6) в `data/`. Из корня checkout выполните:

   ```sh
   python -m unittest discover -s tests
   python -m vk_mail_search.predict --queries data/queries_dev.jsonl --out predictions.jsonl --k 100
   python -m vk_mail_search.evaluate --pred predictions.jsonl --k 100
   python -m vk_mail_search.evaluate --searcher period:cover --k 100
   ```

2. Запустите локальный сервер. В другом терминале повторите нагрузку. Для второго профиля задайте серверу `VK_SEARCHER=period:cover` и перезапустите его.

   ```sh
   python -m uvicorn vk_mail_search.api:app --host 127.0.0.1 --port 8000
   python scripts/load_test.py --url http://127.0.0.1:8000 --queries data/queries_dev.jsonl --calls 1000 --clients 8 --k 10
   ```

3. Для показа откройте ящик с контейнерными уведомлениями, найдите погрузки за указанный день и откройте результат. В ветке сводки дополнительно покажите группировку писем за тот же день. [Готовые запросы, даты и шаги демо](https://github.com/ttm545/b2baihacatondamirhuesos/blob/f5050fbc60cfbe3e24e55ffbd34f4c2de5f9d8f0/docs/demo.md)
