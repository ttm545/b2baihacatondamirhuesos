# Векторный поиск VK Почты

`DenseSearcher(docs)` реализует [общий контракт](decisions.md#d3-контракт-поисковика). Передайте документы с полями `doc_id`, `synthetic_user`, `doc_dt` и `doc`. В тексте корпуса уже содержатся заголовки письма, когда организаторы их предоставили.

При первом запуске кодируем письма пакетами локальной `deepvk/USER2-base`. Для писем, которые выходят за рабочее окно 512 токенов, кодируем фрагменты с перекрытием 64 токена и берём лучший косинус на письмо. Матрица и границы фрагментов хранятся в `VK_CACHE_DIR` (по умолчанию `.cache/`). Ключ кэша зависит от содержимого корпуса, ревизии модели и настройки фрагментов. При последующих запусках векторы загружаются с диска, в запросе кодируется только поисковая фраза.

## Установка и проверка

Установите зависимости в чистом окружении Python 3.11–3.14 и задайте путь к распакованному архиву:

```sh
python -m pip install -r requirements-embeddings.txt
export VK_DATA_DIR=/path/to/unpacked/dataset
export VK_CACHE_DIR="$PWD/.cache"
```

Чтобы построить кэш и проверить первый публичный запрос:

```sh
python - <<'PY'
import json
import logging
import os
from pathlib import Path
from types import SimpleNamespace

from vk_mail_search.dense import DenseSearcher

logging.basicConfig(level=logging.INFO)
data = Path(os.environ['VK_DATA_DIR'])
with (data / 'documents.jsonl').open(encoding='utf-8') as files:
    searcher = DenseSearcher(SimpleNamespace(**json.loads(line)) for line in files if line.strip())
with (data / 'queries_dev.jsonl').open(encoding='utf-8') as files:
    item = json.loads(next(files))
print(searcher.search(item['query'], item['synthetic_user'], item['query_date'], 10))
print(searcher.cache_path)
PY
```

В `search(query, mailbox, as_of, k)` учитываются только документы указанного ящика. Письма с известной датой позже `as_of` исключаются, письма с неизвестной датой остаются. Результат содержит максимум `k` уникальных `doc_id` с оценками.

На публичном корпусе самое длинное письмо занимает 6 618 токенов с учётом промпта, при максимуме модели 8 192. Окно 512 — настройка поиска по фрагментам, а не ограничение USER2-base.

После подключения общей ветки с оценщиком запустите стандартный бенчмарк:

```sh
python -m vk_mail_search.evaluate --searcher dense --k 10 --out predictions-dense.jsonl
```

Оценщик прогревает поиск, проверяет границы ящика и даты и считает Recall, nDCG и MRR на K = 5, 10 и 20. Тайминг относится к `search()` при K = 10. Серверный p99 измеряется отдельно через HTTP API.

## Поиск внутри периода

Прогон на 99 запросах, `dev` (`cc427e4`), K=10 и 10 прогревочных запросов. Время — вызов `search()` на CPU Apple M4, без HTTP.

| Поисковик | Recall@10 | nDCG@10 | MRR@10 | p99, мс |
| --- | ---: | ---: | ---: | ---: |
| `dated:bm25` | 0,8932 | 0,9239 | 0,9217 | 1,63 |
| `dated:dense` | 0,8783 | 0,9245 | 0,9434 | 32,76 |
| `dated:hybrid` | 0,8892 | 0,9365 | 0,9680 | 27,20 |
| `dated:hybrid:w_bm25=0.7,w_dense=0.3` | 0,8901 | 0,9346 | 0,9596 | 22,24 |
| `dated:hybrid:mode=score,w_bm25=0.5,w_dense=0.5` | 0,8912 | 0,9315 | 0,9498 | 22,76 |
| `dated:hybrid:mode=score,w_bm25=0.3,w_dense=0.7` | 0,8905 | 0,9277 | 0,9465 | 28,36 |

Стандартный `dated:hybrid` дал лучший nDCG@10 (+1,25 процентного пункта к `dated:bm25`), с уступкой по Recall@10 (−0,40 п.п.). Из 14 запросов про контейнеры и платежи, где nDCG@10 у BM25 был ниже 1, улучшились 9, ухудшились 4 и один остался без изменений. Ни один из этих 14 не достиг 1. Среди остальных 85 улучшились 9, ухудшились 9, не изменились 67. Семь ранее идеальных выдач потеряли nDCG.

Повтор после обновления от `dev` (`86ec11d`, BM25 с темой и префиксами), те же 99 запросов и K=10:

| Поисковик | Recall@10 | nDCG@10 | MRR@10 | p99, мс |
| --- | ---: | ---: | ---: | ---: |
| `dated:bm25` | 0,9246 | 0,9542 | 0,9478 | 2,07 |
| `dated:dense` | 0,8783 | 0,9245 | 0,9434 | 25,22 |
| `dated:hybrid` | 0,9142 | 0,9537 | 0,9697 | 22,87 |
| `dated:hybrid:w_bm25=0.7,w_dense=0.3` | 0,9208 | 0,9632 | 0,9751 | 26,06 |
| `dated:hybrid:mode=score,w_bm25=0.5,w_dense=0.5` | 0,9066 | 0,9460 | 0,9686 | 114,46 |
| `dated:hybrid:mode=score,w_bm25=0.3,w_dense=0.7` | 0,9054 | 0,9402 | 0,9518 | 24,87 |

В повторе лучший по nDCG — RRF с весами 0,7/0,3. Из исходных 14 запросов улучшились 8, ухудшились 3, не изменились 3. Среди остальных 85 улучшились 9, ухудшились 7, не изменились 69. Показатель Recall@10 по всему набору немного уступил BM25.

Выброс 56,431 мс в прежнем прогоне не воспроизвёлся в пяти проходах по 99 запросам. p99 всего вызова составил 22,948 мс, отдельно кодирования — 22,736, скалярного произведения и агрегации — 0,507, фильтра и сортировки — 1,056. У самого медленного вызова 31,737 из 32,832 мс заняло кодирование. Наблюдавшаяся там сборка мусора заняла 0,030 мс. p99 после смены ящика — 22,698 мс, без смены — 22,948 мс. Два p99 из разных прогонов вычитать нельзя: на 99 измерениях это единственный максимум каждого прогона. Свидетельств выброса в ранжировании `dense.py` не нашли, код оставлен без изменения.

## Замер на сервере

Отдельный стенд: <https://vk-mail.597d550b.sslip.io/>. API из `dev` (`cc427e4`) работает в одном процессе с `VK_SEARCHER=dated:bm25`. Хост — один vCPU Intel Xeon Skylake, 1,9 ГиБ ОЗУ, вычислительного GPU нет. Готовый кэш на 51 294 688 байт перенесён и сверён по SHA-256, смонтирован в `VK_CACHE_DIR`. Текущий BM25 кэш векторов не использует.

```sh
python scripts/load_test.py --url https://vk-mail.597d550b.sslip.io \
    --queries "$VK_DATA_DIR/queries_dev.jsonl" --clients 8 --calls 1000 --k 10
```

Скрипт циклически берёт все 99 запросов, использует отдельное HTTPS-соединение и два прогревочных вызова на клиента. `took_ms` измерен API, `client_ms` включает сеть и получение тела ответа. Если Python не видит корневые сертификаты macOS, запускайте с `SSL_CERT_FILE=/etc/ssl/cert.pem`. Проверка TLS остаётся включённой.

1000 из 1000 запросов прошли успешно, 19,14 запроса/с. p50/p95/p99 в API: **2,854 / 13,772 / 22,686 мс**. По времени внешнего HTTPS-клиента: **160,610 / 454,541 / 713,664 мс**. Это замер `dated:bm25`, с которого запускается стенд.
